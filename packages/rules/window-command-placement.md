# Где размещать команды окна и компонента

Авторская политика AG, 2026-10-31. Область действия команды определяет её место. Частота определяет заметность, узнаваемость — возможность заменить подпись иконкой. Это три отдельных решения. Матрица уточняет общую рекомендацию «частые команды в native toolbar», а не переносит туда все частые кнопки.

| Область действия | Основное место | Примеры и ограничения |
|---|---|---|
| Приложение целиком | Системное меню приложения; постоянная навигация | Настройки приложения, помощь, переходы между разделами. Частый shortcut допустим в toolbar, но обычные редкие настройки не требуют своей полосы |
| Текущее окно или рабочее пространство | Настоящая системная панель окна при поддержке платформы; иначе одна web-шапка | Back/Forward, выбор проекта/документа, управление панелями, общий поиск. Объект действия однозначен при смене фокуса |
| Текущий документ/экран | Его общая шапка; native toolbar только при однозначном активном документе | Сохранить документ, обновить весь экран. В split-view команда не должна неожиданно менять адресата |
| Отдельный компонент или выделенный объект | Компактная панель компонента, его заголовок или непосредственно рядом с объектом | Копировать код, поиск внутри блока, перенос строк, масштаб графика, фильтр таблицы, действия строки. Название общего окна не объясняет их адресата |
| Редкая вторичная команда | Подписанный overflow соответствующей области | Меню компонента для компонента, меню окна для окна. Не смешивать их без названных групп |
| Опасное/значимое подтверждение | Рядом с затронутым объектом, с явной подписью и последствиями | Не превращать удаление данных или разрешение доступа в безымянную иконку ради компактности |

## Когда переносить в native-панель

Перенос допустим, если выполнены все условия:

1. Команда относится ко всему окну/рабочему пространству либо однозначному активному документу. Если два блока могут независимо выполнить действие, оставьте его в блоке или явно назовите адресата глобальной команды.
2. Команду полезно иметь постоянно: это частая навигация/операция, а не настройка, ради которой сохраняется целая пустая полоса.
3. Платформа предоставляет настоящую панель и поддерживает нужный контрол. Сохраняются системные кнопки, перемещение окна, название контекста и доступная область для заголовка. Нельзя решать переполнение наложением кнопок на заголовок.
4. Есть единый обработчик/command ID и владелец состояния. Native вызывает ту же разрешённую операцию, что web-вариант; состояния enabled, hidden, selected/toggle, pending и текущий объект синхронизированы в необходимом для команды объёме. Неподдерживаемое состояние — причина оставить web-контрол.
5. Перед скрытием web-действия подтверждена готовность именно этой команды в текущем окне и документе. Флаг «это native-приложение» или наличие toolbar сами по себе недостаточны. При reload/сбое bridge подтверждение инвалидируется и fallback восстанавливается.
6. Проверены клавиатура/доступное имя, состояние, фокус между native и содержимым, узкое окно, 200% текст, темы и fallback. Неизвестное не заменяется словом PASS.

## Когда удалять отдельную полосу

Для каждой команды старой полосы укажите `commandId → область/объект → новое место → состояние → fallback`. Удаляйте ряд только когда все действия доступны в подходящих местах и в нём не осталось уникального контекста, фильтра или статуса. Если оставшаяся команда локальная, перенесите её к компоненту; если редкая общая — в доступное меню. Не оставляйте пустую высоту, divider, margin или скрытый фокусируемый дубликат.

Обычное native-меню и toolbar могут предоставлять одну команду со стандартным shortcut. Это полезная альтернативная доступность, не повод рисовать второй идентичный HTML-toolbar. Второй ряд оправдан самостоятельной задачей: например, фильтрами текущей таблицы, редактором форматирования или инструментами канвы. Он должен быть подписан контекстом и давать функции, отсутствующие в системной строке.

## Компактные действия и подсказки

Выбирайте icon-only по разделу icons: знакомая операция, ясный адресат, доступное имя, видимый фокус, полноценный hit target. По AG-default знакомые операции редактора могут быть компактными по умолчанию с вариантом `toolbarMode: "labeled"`. Подсказка дополняет имя; задержка pointer-hover 250 мс — настраиваемое значение AG, не требование WCAG. Для web-компонентов используйте общий `bindTooltip`/inline-help lifecycle; не переносите эту JS-задержку на системные tooltip без поддержки ОС. Важные/непонятные операции сохраняют видимый текст. Touch не должен зависеть от hover.

## Проверка результата

Сравните до/после: число верхних рядов и занятую ими высоту; число недоступных команд (цель 0); дублирующие видимые команды одного scope; способность выполнить сценарии из меню, клавиатуры и компонента. Уменьшение высоты — геометрический результат, не доказательство ускорения пользователя. Для такого вывода нужны измерения задач: успешность, время и ошибки в одинаковых условиях. Не задан универсальный лимит количества иконок или рядов.

## Основания и границы

Apple HIG описывает toolbar как доступ к частым командам, навигации и поиску и рекомендует осмысленные группы без перегрузки. W3C требует программно определимых имён, ролей и состояний. Приведённые матрица scope, порядок проверки и удаление дублирующего ряда — политика AG на основе этих принципов, не цитата или автоматическая проверка соответствия ОС.

- [Apple HIG — Toolbars](https://developer.apple.com/design/human-interface-guidelines/toolbars)
- [W3C — Name, Role, Value](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html)
- [W3C — Content on Hover or Focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html)

Правила не подтверждают реализацию адаптера, производительность, native/AT-тестирование или обновление установленного приложения.
