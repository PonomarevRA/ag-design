# Ширина компонентов и внутренних колонок

Сначала измеряйте корень, затем значимые внутренние колонки: исправная ширина внешней карточки не исключает схлопывания текста внутри. Используйте общий `auditInterface(localRoot).layoutWidths` или `auditLayoutWidths(localRoot)` из `@ag-design/components/audit`. Вывод — анонимные геометрические цели без содержимого, private IDs и значений полей.

## Объявления и диагностика

На принадлежащем компоненту корне задайте `data-ag-width="fill"`, если он заполняет выделенную обёртку. На значимой текстовой колонке — `data-ag-width="content"`. Минимум12em — конфигурируемая эвристика AG, не универсальная норма WCAG. Для обоснованного узкого элемента задайте `data-ag-width-min-em="2"` или другое число0.5..100. Не маркируйте узкую иконку/рейл как длинный текст. Для root-fill в нескольких flex/grid tracks используйте отдельную выделенную обёртку: неподдержанный allocated slot остаётся unknown, а не ошибкой и не PASS.

Аудит обнаруживает необъявленные inline-size-contained корни и подозрительно узкие текстовые колонки как inferred/unknown. Это кандидаты для разметки/ревью, не автоматически доказанная ошибка. Подтверждённый дефицит больше1CSSpx даёт fail. Скрытое исключается с причиной; visible disabled элементы проверяются. Detached/unmeasurable/transform/scale/rotate/translate/zoom/вертикальное письмо/лимит обхода остаются unknown. Семантику, AT и оптическое качество по числам не подтверждаем.

## Перед завершением задачи

Зафиксируйте revision и инвентарь всех изменённых визуальных блоков/значимых колонок. После загрузки шрифтов и стабилизации layout выполните `normal`, `narrow` (фактический `innerWidth<=320CSSpx`), `text200` и `narrow-text200`. Это диагностическая матрица AG. Не выдавайте200% zoom за удвоенный CSSfont: для этого контракта подтвердите рост измеренного fontSize каждого видимого target относительно normal. WCAG допускает разные механизмы увеличения; этот runner покрывает один конкретный способ и не является сертификацией.

Сохраните IDs targets из всех сценариев и отправьте `layout_width_review` в `design_evaluate_interface`. Формат: `{revision,blocks:[{blockId,targets:["width-1",...],samples:[{scenarioId,revision,report:audit.layoutWidths},...]}],exclusions?:[{blockId,reason}]}`. Отдельные исключения нужны только для явно невизуальных/неизменённых блоков. Все изменённые blocks из `changed_block_review` должны быть представлены или обоснованно исключены. Недостающие, устаревшие, truncated, inferred и не подтверждающие viewport/рост шрифта цели перечислены в `layoutWidthReview.unchecked`; server пересчитывает статус по фактам и не доверяет ручному pass/нулевому deficit. По всем исходным целям сохранить назначение и минимум между сценариями. Разбейте явно большой scope: максимум128width cases на отчёт.

Условие завершения: current detailed requirements, `layoutWidthReview.gate=pass`, `changedBlockReview.unchecked=[]` и `completionGate=pass`. Для `design_report_checks` тот же пакет входит в `report.designReview.layoutWidthReview`; ручные метрики0 не обходят ширину. Новый policyHash делает прежние PASS неактуальными — перечитайте brief и выполните текущие проверки. Geometry не заменяет клавиатуру, реальный reflow, доступность, читабельность или совместимость хоста.

## Исправления

Не растягивайте высоту, чтобы спрятать схлопнувшуюся ширину. Для container-type:inline-size задавайте корректный inline-size/box-sizing в своём allocated wrapper. Адаптацию внутренних колонок привязывайте к ширине компонента, а не только окна. Проверяйте computed tracks и специфичность каскада: вертикальные tabs могут перекрыть container query. Длинный настоящий инструмент можно оставить в ограниченной top-aligned прокрутке каталога, сохранив доступность последнего действия. Не меняйте Pinterest-порядок ради этих проверок.
